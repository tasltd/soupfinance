SOUPFIN-145 — applyTemplate and coaTemplate/index

Backend plan for soupmarkets-web, branch authentication-base-on-multi-tenancy-descriminator. Written 2026-10-12 from the SoupFinance repository, which may not change backend code (.claude/rules/backend-changes-workflow.md, SOUPFIN-13 directive). Builds on SOUPFIN-143.

Goal. An admin or finance user can list the chart-of-accounts templates, and apply one to their own tenant with optional country and industry overlays. They can preview first with a dry run, which writes nothing. Applying the same selection twice creates nothing the second time.

3. Endpoint contract

The response shapes below were produced by running apply.mjs, then trimmed to two rows per list. The Groovy port must return the same keys.

GET /rest/coaTemplate/index.json

4. Rules the endpoint enforces

  1. Match on number, then on name. An existing account (archived or not) with the template number is skipped with number-exists. Otherwise one with the same name, compared case-insensitively, is skipped with name-exists. Number comparison is on the string form, because ledger_account.number is bigint on the seed database.
  2. Categories match by name, case-insensitively. The old registration seed wrote "Other Assets" in mixed case; it is reused, not duplicated.
  3. Parent links resolve to whatever holds the parent number. If the tenant already has 5000, a new 5085 hangs under that account, not under a missing one.
  4. Singleton roles are never stamped twice. If another account already carries ACCOUNTS_RECEIVABLE, the template's 1200 is created without the role and a line goes into problems.
  5. Tenant scope comes from the session only. The tenant is Tenants.currentId() as resolved by SoupDiscriminatorTenantResolver. Any tenantId or account in the body is ignored, and the bind must not pick it up (use a command object with only template, overlays, dryRun). No method on this path is @WithoutTenant.
  6. All or nothing. A real run is one transaction. If any insert fails, every row from that apply rolls back.
  7. A dry run writes nothing. It runs the same planning code inside a read-only transaction.

// LedgerAccountController
@Secured(["ROLE_ADMIN", "ROLE_FINANCE"])   // overrides the class-level ROLE_USER grant
def applyTemplate(CoaApplyCommand cmd) {
    withForm {
        Account account = Account.get(Tenants.currentId())
        try {
            CoaApplyResult result = coaTemplateService.apply(account, cmd)
            render(status: 200, contentType: 'application/json', text: (result.toMap() as JSON).toString())
        } catch (CoaApplyException e) {          // 422 and 500 cases from section 3
            render(status: e.status, contentType: 'application/json',
                   text: ([status: e.status, code: e.code, message: e.message] as JSON).toString())
        } catch (org.springframework.dao.DataIntegrityViolationException e) {
            render(status: 409, contentType: 'application/json',
                   text: ([status: 409, code: 'apply-conflict',
                          message: 'Another apply ran at the same time. Nothing was saved; try again.'] as JSON).toString())
        }
    }.invalidToken {
        render(status: 409, contentType: 'application/json',
               text: ([status: 409, code: 'invalid-token',
                      message: 'The form token is missing or was already used. Fetch /rest/ledgerAccount/create.json and retry.'] as JSON).toString())
    }
}

// CoaTemplateService.apply, real run
@Transactional
CoaApplyResult apply(Account account, CoaApplyCommand cmd) {
    Selection sel = resolveSelection(cmd)                  // throws CoaApplyException(422)
    ComposedTemplate composed = compose(sel)
    List<String> invalid = validate(composed)
    if (invalid) throw new CoaApplyException(500, 'template-invalid', invalid.join('; '))
    if (!cmd.dryRun) Account.lock(account.id)              // serialise concurrent applies per tenant
    Plan plan = planApply(composed)                        // reads LedgerAccount/Category, archived included
    if (!cmd.dryRun) writePlan(plan)                       // categories first, then accounts in number order
    return CoaApplyResult.from(cmd, composed, plan)
}

Why lock the Account row. Two applies in parallel would both plan the same inserts, and the second would fail on the unique index. Account.lock(id) is a SELECT FOR UPDATE on the tenant root, so the second apply waits, then plans against the first one's rows and creates nothing. The 409 branch stays as a backstop.

Why both actions take ROLE_FINANCE but not ROLE_USER. Applying a template creates up to 90 accounts in one go; that is a set-up decision, not a day-to-day entry. Listing is harmless, but the picker is only useful to someone who can apply, so the two match.
