1. What the backend does today

The parent plan says registration never seeds a chart of accounts. On the multi-tenancy branch that is no longer true. AccountRegistrationService.createDefaultChartOfAccounts already seeds a TRADING or SERVICES chart. That seed has the wrong shape, though, so posting and reports still fail. Every row below was checked against the code or the LXC database on 2026-10-10.

3. Design decisions

DecisionWhyReversible?
Templates are JSON files under grails-app/conf/seed-data/coa/, read into plain Groovy objects CoaTemplate, CoaTemplateAccount and CoaTemplateCategory. They are not GORM tables.Templates are global, but every finance table here is multi-tenant. A template table would need @WithoutTenant plumbing and a migration. JSON ships with the WAR, is reviewed in a diff, and follows the existing seed-data/ loader.Yes. A table can be added later if admins need to edit templates in the UI.
Add enum LedgerAccountType and a nullable LedgerAccount.accountType column.Posting should find "the A/R account" by role, not by a name a user can change. The enum also gives SOUPFIN-145 and SOUPFIN-147 a stable vocabulary.Mostly: a new nullable column. Dropping it later is a migration.
Also set Account.defaultReceivableAccount and defaultPayableAccount at seed time.Today's posting code reads those FKs. Setting them makes invoices and bills post correctly with no posting-code change.Yes.
Keep the category names the backend looks up, spelled exactly, including SHORT -TERM LIABILITIES.Eleven code paths find categories by name. Renaming them breaks posting and client registration. LedgerAccountCategory.toString() already title-cases them for display.Yes, once those lookups move to accountType.
Income and expense categories use ledgerGroup EQUITY + ledgerSubGroup INCOME/EXPENSE under RETAINED EARNINGS.The broker template, the ServiceDescription validator and the income statement all use this convention. RETAINED EARNINGS keeps a null subgroup so it stays off the income statement (the broker template gives it ASSET, which is a bug).Yes.
Add TaxEntry.liabilityLedgerAccount and TaxEntry.recoverableLedgerAccount (nullable), linked from the country overlay.Act 1151 requires VAT, NHIL and GETFund on separate lines and makes each deductible. Each tax needs its own output and input account.Yes: nullable FKs. Switching posting to them is a separate task.
Point each seeded service description at a template account.Otherwise checkAndGetLedgerAccount() creates one "<name> Account" per description. That adds 32 accounts and breaks the lean target.Yes.
Overlays may only add, remove or explicitly replace (replace:true). Silent collisions are errors.A typo in an overlay must fail the build, not overwrite Accounts Receivable.Yes.

5. Seeding algorithm

  1. Compose. Base template for account.businessLicenceCategory, then the country overlay, then the industry overlay. The overlay contract errors are fatal: log them and seed nothing.
  2. Categories. Create the categories categoriesFor() returns, parents first. Match existing rows by name, case-insensitively, because the MariaDB unique index is case-insensitive too. Set account, systemCategory=true, deletable=false, and editable from the catalogue.
  3. Accounts. Create each account. Match an existing account by number first, then by name; skip it if found, so applying a template twice adds nothing. Set currency to the tenant currency and copy the flags and accountType.
  4. Parents. Second pass: set parentAccount by number.
  5. Defaults. Set account.defaultReceivableAccount to the ACCOUNTS_RECEIVABLE account and defaultPayableAccount to ACCOUNTS_PAYABLE, but only when they are null.
  6. Singleton guard. If a singleton role is already held by another account, do not stamp the role on a second one. Report it in problems.
  7. Transaction. Run inside the caller's transaction, as today: a separate transaction deadlocks against the new Account row (see the comment in createDefaultChartOfAccounts). Use save(flush: false) and one flush at the end.
  8. Dry run. With dryRun=true, return the composed plan and what would be created or skipped, without saving. SOUPFIN-145 and SOUPFIN-147 build their preview on this.
